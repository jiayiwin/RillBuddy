# 桌面宠物产品策略：通用工作陪伴、记忆与行动入口

## 产品判断

桌宠真正的价值不是让用户盯着自己，也不是用提醒把用户按回“专注状态”。它应该在桌边替用户保留一点工作上下文，在真正需要用户时递上一个明确的下一步，同时提供一个轻、稳定、没有压力的陪伴对象。

建议把产品定位为：

> 一只在桌边陪着你的通用工作宠物，替你记住事情停在哪里、哪些事需要你处理，并在你准备好时帮你继续。

这和“注意力管理”有交集，但中心不同：注意力管理关心用户有没有持续盯着任务；我们的核心应当是用户能不能更少地丢失上下文、更快地恢复工作、更轻松地完成下一步。

桌宠是入口和情绪载体，真正有用的能力来自它背后的工作记忆、任务整理和行动服务。

## 方向修正：Agent 是一个类别，不是产品身份

这只宠物不应该被定义成“agent 宠物”。用户的工作由很多来源共同组成：agent 只是其中一类，而且是我们最适合先做好的那一类。

更稳定的产品抽象是：

```text
来源 Source       事实 Activity       工作项 Work Item       下一步 Action
agent             session / tool      修复登录问题           打开会话
日历              meeting / reminder  周报准备               打开会议材料
邮件              thread / deadline   回复客户               打开邮件
Git / CI           commit / build      发布版本               查看失败构建
待办 / 项目        task / milestone    设计评审               标记完成
文件 / 窗口        edit / context      当前正在写的文档       回到上次位置
```

宠物面对的是用户的“当前工作世界”，而不是某个 agent 的进程。agent 的独特能力仍然保留：它能报告会话状态、等待权限、给出下一步、执行安全动作；但这些能力通过 `AgentAdapter` 接入统一的工作模型，不再决定产品的命名、主界面和数据结构。

### 产品语言也要变

- 产品名和桌宠称呼使用“工作宠物 / 桌面陪伴”，不要使用“agent 宠物”；
- 第一版可以有「Agent」筛选和 agent 专属卡片，但它属于「来源」或「工具」分类；
- “agent 工作台”逐步改为“工作台”，其中有 Agent、日历、邮件、项目、CI 等来源；
- 介绍产品时说“支持 agent”，而不是“替 agent 看着你工作”。

这样既保留了当前最强的开发者场景，也为非 agent 工作留下自然的位置。

### 通用定位不等于第一天接所有服务

产品身份可以通用，首期能力仍要聚焦。建议把边界定成“桌面上的工作连续性”，而不是一开始就做成日历、邮件、健康、习惯和项目管理的总入口。

首期优先接三类来源：

1. **Agent**：状态丰富、需要用户处理的事件明确，是当前最强的切入点；
2. **本地工作上下文**：项目、窗口、文件和最近位置，解决“从哪里继续”；
3. **用户主动捕获**：一句话、语音或选中文字，解决“先帮我记住”。

日历、邮件、Git/CI 和项目系统作为第二批来源接入，前提是它们能提供明确的下一步和可靠的打开/处理动作。任何来源如果只能带来更多通知、不能降低行动成本，就不应为了“通用”而接入。

## 日历和邮件怎么接入

日历和邮件都应通过 `SourceAdapter` 接入统一工作台。适配器负责授权、增量同步和回写动作；桌宠只接收标准化的 `SourceSnapshot`，不直接理解 Google、Microsoft 或飞书的 API。

```text
Provider API / Webhook
        ↓
SourceAdapter（授权、游标、去重、限流）
        ↓
SourceSnapshot + WorkItem
        ↓
需要你 / 即将发生 / 等待中 / 已完成
        ↓
工作台、桌宠摘要、回到原应用的 Action
```

### 日历适配器

第一版只读同步，不替用户自动改日程。每个日历事件转换成一个工作项，但只有满足条件时才进入“需要你”：

- 距离开始时间进入准备窗口，例如 30 分钟；
- 事件有会议链接、地点或需要准备的材料；
- 用户明确标记为重要；
- 事件已经开始但用户尚未打开相关页面。

日历工作项建议包含开始/结束时间、会议链接、地点、参会人数和打开原日历的动作。桌宠表达的重点是“还有 20 分钟，需要准备什么”，而不是“你有一条新日历通知”。可提供的动作包括：打开会议、打开准备材料、记录一个会后事项、稍后提醒。创建、移动、取消会议属于高风险写操作，必须在工作台确认后回到原日历执行。

同步方式按提供商选择：优先使用 webhook / push，后台再用增量游标补偿；没有 webhook 时使用 5–15 分钟轮询。同步只保存事件 id、时间、标题、链接和用户选中的字段，默认不把参会人的完整信息和会议正文复制到宠物数据库。

### 邮件适配器

邮件不能按“未读数”接入，否则桌宠会变成第二个收件箱。第一版只把可能需要行动的线程转成工作项：

- 用户标记的重要邮件；
- 明确要求回复、确认、提供材料或做决定的邮件；
- 有截止日期且尚未处理的线程；
- 用户手动转交给桌宠的邮件。

桌宠只说“有一封需要你决定的邮件”，工作台显示来源、主题、截止时间和短摘要。默认不把完整邮件正文推到桌面，也不自动生成或发送回复；可以提供“打开线程”“记为稍后”“提取截止日期”“写草稿”，发送动作始终回到邮件客户端并要求用户确认。

邮件同步使用 provider 的 history cursor / delta token，保存游标、线程 id 和去重键，避免每次重新扫描整个邮箱。用户可以按账户、文件夹、发件人或标签设置允许范围；私人账户和工作账户应分开显示、分开撤销授权。

### 授权和隐私

日历和邮件都要遵循最小权限：

1. 首次只申请读取和打开原应用的权限；
2. 写入、发信、改会议作为单独的二次授权；
3. token 存在本机凭据存储，不写入 `config.yaml` 或普通日志；
4. 工作台显示每条数据来自哪个账户、最后同步时间和权限范围；
5. 用户可暂停同步、删除本地缓存、撤销单个来源；
6. 桌宠在安静模式下不主动播报邮件和会议，但来源仍可在工作台查看。

### 首期落地顺序

建议先做一个 provider 的只读适配器，再扩展通用协议：

1. 日历只读：即将开始、需要准备、正在进行；
2. 邮件只读：重要线程、明确截止日期、用户手动转交；
3. 工作台动作：打开原页面、稍后提醒、转成任务；
4. 用户确认后的草稿和会议变更；
5. 再接第二个 provider。

如果当前团队主要使用飞书，首期可以先做飞书日历和飞书邮箱；通用 `SourceAdapter` 保持 provider-neutral，之后再接 Google Calendar/Gmail 和 Outlook/Microsoft 365。这样产品先验证“来源 → 工作项 → 下一步”的价值，不会一开始陷入多平台授权和字段差异。

### 通用模型应该从第一天存在

即使第一阶段只接 agent，代码和接口也应使用通用字段：

```rust
struct SourceRef {
    kind: String,        // agent | calendar | mail | git | project | local
    id: String,
    name: String,
}

struct WorkItem {
    id: String,
    title: String,
    source: SourceRef,
    state: WorkState,    // needs_you | working | blocked | done | parked
    next_action: Option<ActionRef>,
    project: Option<String>,
    started_at: Option<u64>,
    updated_at: u64,
    evidence: Vec<EvidenceRef>,
}

struct ActionRef {
    label: String,
    kind: String,        // focus | approve | reply | retry | complete | snooze
    target: serde_json::Value,
    reversible: bool,
}
```

`AgentSummary` 可以作为 `SourceSummary` 的一种特化视图，第一阶段兼容现有 session 数据；未来新增来源不需要重做桌宠状态、优先级和工作台。

## 从竞品得到的启发

截图中的产品大致分成两类：

- 电脑端宠物：在屏幕边陪伴、提醒休息、用互动维持唤醒度；
- 手机端虚拟宠物：用拆解、打卡、养成和奖励推动行为完成。

它们解决了“我需要一个轻量的陪伴对象”和“我希望有人提醒我”的需求，但容易遇到三个空缺：

1. 提醒之后没有替用户减少下一步的成本；
2. 用户离开或切换任务后，工作上下文容易丢失；
3. 养成、积分和连续打卡可能把负担转成另一套负担。

我们应该吸收它们的陪伴感和低压力互动，避开把用户停留时间、打卡天数或被提醒次数当成产品成功。

## 用户真正需要什么

### 1. 我现在该从哪里继续？

用户真正困难的常常不是没有任务，而是重新进入任务需要重新读文件、回忆决定、寻找窗口和判断下一步。

桌宠可以提供：

- 上次停下的位置；
- 最近一次明确的下一步；
- 相关项目、会话和窗口；
- 一个“继续”动作，直接回到正确位置。

这比“你已经专注了 25 分钟”更接近工作本身的价值。

### 2. 我离开时发生了什么？

离开会议、吃饭或睡觉后，用户需要知道变化，而不是收到一串日志。

桌宠应该把变化压成可行动的交接：

```text
你离开期间：
✓ 2 件完成
! 1 件等你批准
· 1 件仍在运行

[查看等你] [继续未完成]
```

摘要必须带来源和时间范围，避免把旧状态误报成新事件。

### 3. 哪些事真的需要我处理？

多个 agent、项目和工具同时运行时，用户不缺状态，缺的是排序后的“现在需要我做什么”。

桌宠应该把事件分成三类：

- **需要我**：批准、回答、选择、修复冲突；
- **可以等**：正在运行、排队、等待外部资源；
- **已经完成**：只需确认或稍后查看。

只有第一类主动打扰，其余放在悬停卡和工作台里；工作台默认展示 Agent，也能逐步接入其他来源。

### 4. 我脑子里有件事，先帮我放下来

用户需要一个比打开任务管理器更轻的入口，把一句想法、一个承诺或一段选中的文字放下来。

桌宠可以支持：

- 快捷键、右键、语音、选中文字快速捕获；
- 自动判断是任务、备注、等待条件还是普通备忘；
- 把“等某个 agent 做完”绑定到 agent/session；
- 在合适的时机提醒，而不是立刻催促。

捕获的结果必须能被用户修改、合并、完成和删除，不能变成宠物替用户积累的新收件箱。

### 5. 我需要一个明确的下一步，而不是更大的计划

当任务卡住时，最有用的帮助往往是把它缩成一个可执行动作：打开文件、查看错误、回复一个问题、选择一项批准。

宠物可以提供“下一步建议”，但必须把建议和证据分开：

- 事实：agent 最近在 `project-a` 的 `session-b` 里等待权限；
- 建议：打开批准卡；
- 不确定性：这是根据最近事件推断的，可能已经过期。

### 6. 我想有人在，但不想被监督

陪伴需要持续存在感，但不应把用户变成被观察的对象。

宠物可以用表情、姿态、轻微互动和固定仪式表达“我在这里”；提醒需要用户可控、可暂停、可解释。用户不应该为了让宠物开心而完成工作，也不应该因为没有完成打卡而被宠物惩罚。

### 7. 我希望开始和结束都有边界

用户需要开始工作时少一点启动摩擦，结束工作时少一点悬而未决。

- 开始：显示上次未完成事项和一个推荐入口；
- 中间：保持安静，只处理需要用户的事件；
- 结束：生成简短交接，记录每个任务停在哪，给出明天的恢复入口。

这比强制计时、连续打卡或固定频率提醒更尊重不同人的节奏。

## 产品能力分层

### A. 陪伴层：让它值得留在桌边

- 一只稳定的桌面角色，有自己的表情、声音、动作和可调节的性格；
- 轻量的点击、抚摸、喂食、小游戏和换装；
- 记得用户选择过的偏好和重要时刻，但不把所有行为都量化成分数；
- 没事时安静存在，有事时给出清楚的理由。

陪伴层的目标是降低使用门槛和情绪压力，不负责管理任务真相。

### B. 工作记忆层：替用户保留上下文

- 当前正在做什么、上次停在哪里、下一步是什么；
- agent/session/task 的关系和最近变化；
- 离开期间的完成、等待、错误和新信息；
- 每日交接和跨天恢复；
- 用户手动捕获的备注和承诺。

工作记忆要以时间和来源为基础，默认本地保存，允许用户查看、修改和删除。

### C. 行动层：把状态变成一个动作

每一条重要消息都应尽量带一个动作：

| 状态 | 可提供的动作 |
|---|---|
| 等待批准 | 允许 / 拒绝 / 交给终端 |
| 等待输入 | 打开对应会话 |
| 工具失败 | 查看错误 / 重试 / 标记已处理 |
| 任务完成 | 查看结果 / 记录下一步 |
| 离开后有变化 | 查看摘要 / 继续某个任务 |
| 只有空闲 | 打开上次未完成事项 |

动作应尽可能是一次点击，且永远显示目标 agent、项目和 session，避免“点了之后才发现操作对象不对”。

### D. 协调层：管理多个 agent，而不是养多个宠物

- 一个全局工作台，Agent 是其中一个来源分类；
- 按“需要我 / 进行中 / 已完成 / 离线”筛选；
- agent、项目、session、task 的下钻关系；
- 等待事项队列和主任务选择；
- 统一的聚焦窗口、复制路径、重试和归档动作。

这正是单宠物方案中必须补上的功能。桌面宠物只做摘要，工作台负责完整可见性，并逐步汇总其他来源。

### E. 节奏与情绪照护层：支持调节，不制造压力

休息、收工、安静模式、烦躁缓冲和久坐提醒仍然有价值，但它们应当由用户选择和情境触发：

- 用户可以设置安静时段和提醒强度；
- 提醒说明“为什么现在提示”，并提供稍后提醒、今天不再提示和关闭；
- 不用“你失败了”“你又拖延了”这类评价语言；
- 休息建议可以连接音乐、拉伸或离开屏幕，但不追踪用户是否照做来惩罚。

心理层要解决的是情绪调节，不是诊断情绪。宠物不应该根据键盘速度、窗口切换或表情“判断你焦虑了”，而应让用户用很低成本主动表达：“我有点烦”“我脑子很乱”“陪我安静一下”“帮我理清”。

## 情绪层的真实需求和机制

### 降低烦躁：先减少刺激，再给选择

烦躁通常不是缺少一条提醒，而是同时有太多未完成事项、声音、弹窗和不确定的下一步。宠物应有一个可随时召唤的「缓一缓」模式：

1. 暂停非必要的气泡、表演和普通通知；
2. 降低动画速度、亮度和声音密度，宠物坐下来陪着，不继续追问；
3. 把当前需要用户处理的事项压成最多两项；
4. 提供三个低负担选择：`先处理一件`、`记下来稍后处理`、`陪我安静 2 分钟`。

关键是减少选择数量，而不是再增加一个复杂的情绪面板。

### 缓解焦虑：把不确定性变成边界清楚的事实

焦虑往往来自“我不知道还有什么没处理、事情会不会失控”。宠物可以提供一个“事情现在到哪了”的小结：

```text
现在有 4 件事：
✓ 2 件已经完成
! 1 件需要你的决定
· 1 件正在等待外部结果

暂时没有其他事项需要你处理。
```

这不是保证事情一定顺利，而是明确告诉用户：已经知道什么、还不知道什么、下一次什么时候再看。对于正在等待的事项，宠物可以替用户设置回看时间，避免用户反复检查。

### 舒缓心情：陪伴先于建议

心情低落时，用户未必想要效率建议。宠物的第一反应应该是存在感，而不是教育：

- 坐到屏幕边缘，动作变慢，保持一段安静；
- 播放用户选择的低刺激声音或熟悉电台；
- 说一句短而具体的话，例如“我在这儿，先不用处理别的”；
- 提供摸一摸、喂糖、看它做一个小动作等不要求产出的互动。

用户主动选择后，才进入呼吸、整理或继续工作的步骤。陪伴本身就是一个完成态，不需要每次都导向任务。

### 从烦乱回到行动：只给一个很小的动作

情绪稳定后不要直接把用户推回完整任务列表。宠物应把恢复分成三个很小的阶段：

1. **落地**：喝水、看远处、做一次缓慢呼吸或伸展；
2. **归拢**：把脑中的几句话记录下来，分成“现在 / 稍后 / 等别人”；
3. **继续**：只推荐一个两到五分钟内可以开始的动作。

动作完成后再问是否继续，避免把“缓一缓”变成另一场强制训练。

## 心理层的交互模式

所有模式都可以从桌宠右键、快捷键或语音进入；默认不需要填写情绪分数。

| 模式 | 宠物做什么 | 用户得到什么 |
|---|---|---|
| **陪我安静** | 降低动画和声音，暂停非必要提示，安静陪伴 2 / 5 / 15 分钟 | 一个可控的低刺激空间 |
| **缓一缓** | 90 秒的呼吸、看远处或伸展引导，可随时跳过 | 从高唤醒状态回落的短仪式 |
| **帮我理清** | 让用户连续说或输入几句话，自动分为现在 / 稍后 / 等待 | 把脑内循环变成外部清单 |
| **我有点烦** | 只显示最重要的一件事，其他事项暂时收起 | 减少当下的选择和刺激 |
| **我有点慌** | 展示已知事实、未知事项、下一次检查时间 | 把不确定性放进边界里 |
| **陪我继续** | 显示上次停点和一个最小下一步 | 在有陪伴的情况下恢复工作 |
| **收工** | 汇总未完成事项，生成明天的恢复卡，并降低夜间刺激 | 让工作有结束感 |

### 模式的共同规则

- 用户可以随时退出、暂停、延长或改成安静陪伴；
- 模式结束后不要求用户汇报心情，也不显示“完成得分”；
- 每次只提出一个选择，最多保留一个次要选项；
- 语言描述当前体验，不给用户贴标签，例如说“事情有点多，我们先收起一部分”，不说“你注意力不足”；
- 情绪模式不改变任务事实，退出后工作台仍能查看完整来源和状态。

## 情绪服务的边界

心理层可以帮助用户调节当下体验，但不应冒充心理治疗或做情绪诊断：

- 不通过隐式监控推断用户的心理状态；
- 不把焦虑、抑郁、烦躁等词作为用户标签或长期画像；
- 不用内疚、失望、掉血、连续天数等机制驱动用户；
- 不承诺“做一次呼吸就会好”或替代专业支持；
- 用户明确表达不想被打扰时，安静模式优先于任何任务提醒；
- 涉及真实工作状态时，情绪安抚不能隐藏“有一件事正在等你”的事实，只能提供稍后处理的边界。

## 心理层的衡量方式

不要用“用户被宠物陪了多久”或“完成了多少次呼吸”衡量心理功能。更有意义的是：

- 用户从烦乱到选择一个下一步所需的时间；
- 用户主动使用“陪我安静 / 帮我理清”的频率；
- 情绪模式后被打断或立即退出的比例；
- 用户是否觉得提醒更少、更可控；
- 离开后能否更顺利地恢复工作；
- 用户是否能随时查看、修改和删除自己的记录。

## 声音与环境层：可以有，但必须由用户掌控

雨声、风声、炉火、海浪、咖啡馆底噪、棕噪音和纯静音都符合“陪伴而不打扰”的定调。它们的价值不在于承诺治疗焦虑，而在于提供一个稳定、可预期、信息密度较低的听觉环境。

### 它可能解决什么

- **遮蔽突发干扰**：持续的低信息声音可以盖住零散的办公室、街道或设备噪音；
- **帮助切换状态**：同一段声音作为开始工作、安静下来或收工的仪式，降低切换成本；
- **提供共同在场感**：宠物在旁边陪着，环境声让“安静”不显得空洞；
- **减少反复检查**：等待 agent、构建或会议时，用户可以听着声音，不必盯着状态变化。

它对每个人的作用不同。雨声可能让一个人放松，也可能让另一个人烦躁；风声、海浪或人声对听觉敏感的人也可能成为新的刺激。因此声音功能应该以“用户愿意再次主动使用”为依据，不宣称固定的心理效果。

### 和宠物功能怎样结合

声音不是独立的音乐播放器，而是宠物模式的一部分：

| 场景 | 宠物 | 声音 | 结束方式 |
|---|---|---|---|
| 陪我安静 | 坐下，动作变慢 | 用户选择的低音量环境声或纯静音 | 2 / 5 / 15 分钟，渐弱 |
| 开始工作 | 指向一个下一步 | 低存在感的雨声、风声或咖啡馆底噪 | 用户设定时长或手动停止 |
| 等待结果 | 保持在旁边，不频繁播报 | 连续、变化少的声音 | 结果需要用户时自动压低并提示 |
| 收工 | 降低亮度，整理交接 | 夜雨、炉火或用户收藏的收工声音 | 播放完后进入安静 |
| 情绪缓冲 | 陪伴，不追问 | 先安静，再由用户选择声音 | 用户随时退出，不要求完成 |

### 交互规则

- 默认关闭自动播放，首次使用时让用户选择，不以声音争夺注意力；
- 每个声音都提供音量、计时、淡入淡出、暂停和收藏；
- 提供“纯静音”作为完整选项，安静不是缺少功能；
- 宠物说话或关键操作时自动 duck（降低）环境声，结束后缓慢恢复；
- 权限批准、错误和其他需要用户处理的事件仍然清楚可见，环境声不能遮住它们；
- 用户进入安静模式后，普通提示不应因为声音播放而重新唤醒；
- 不把播放时长、连续播放天数或“专注分数”变成奖励机制。

### 声音模式契约

声音由宠物模式拥有，而不是由某个 agent 或单独的播放器拥有。每个模式只保存用户的选择，切换模式时自动完成淡入淡出：

```ts
type PetMode = "quiet" | "settle" | "work" | "waiting" | "wind_down";

interface ModeSound {
  mode: PetMode;
  soundscape: "none" | "rain" | "wind" | "fire" | "night" | "cafe" | "brown-noise" | "local";
  volume: number;          // 0..1，用户设置
  durationMin?: number;    // 未设置则持续到用户停止或模式结束
  fadeInMs: number;
  fadeOutMs: number;
}
```

默认关系如下：

| 宠物模式 | 默认声音 | 默认行为 |
|---|---|---|
| `quiet` 陪我安静 | `none` | 只保留宠物的轻微动作，不主动说话 |
| `settle` 缓一缓 | `rain` | 90 秒后渐弱，用户可以跳过 |
| `work` 开始工作 | `wind` 或用户上次选择 | 显示一个下一步，不自动延长工作时长 |
| `waiting` 等待结果 | 用户收藏 | agent 事件到来时短暂降低音量 |
| `wind_down` 收工 | `night` 或 `fire` | 伴随交接卡播放，结束后回到静音 |

模式之间的切换规则：

- 用户主动进入模式时立即生效，声音在 1–2 秒内淡入；
- 宠物说话时降低到原音量的约 25%，说完后缓慢恢复；
- 需要用户处理的事件只降低声音并显示来源，不静默隐藏；
- 用户点停止、关闭桌宠或切换到“纯静音”时立即淡出并记住选择；
- 自动进入 `work` 或 `wind_down` 必须是设置项，默认关闭；
- 退出模式不会改变 agent、任务或工作台中的事实状态。

### 声音内容的取舍

第一版不需要做很大的音频库，先提供少量质量稳定的循环：雨、风、炉火、夜间环境、柔和咖啡馆底噪和棕噪音，再加纯静音。每种声音应有低、中两个混音版本，避免用户为了调音量频繁操作。

后续可以允许本地音频和用户自己的收藏，但要明确音频来源和授权；联网电台仍然是另一个功能，不能和本地环境声混成不可预测的推荐流。

声音的产品定位应是“陪伴和环境控制”，而不是“疗愈音频”。这样既符合整体调性，也不会把个人差异和效果不确定性包装成医学承诺。

## 单宠物的交互原则

### 三层信息密度

单宠物不应试图在身体上显示完整任务列表。采用三层渐进展示：

1. **身体与动作**：只表达整体情绪和紧急程度；
2. **气泡与悬停卡**：给出一件可处理的事情和全局计数；
3. **工作台**：查看所有来源的 task、session、时间线和操作，Agent 是第一批重点来源。

宠物越靠近桌面，信息越少、越稳定；用户主动打开后，信息才变详细。

### 以“下一步”作为最小单位

任何主动提示都应回答三个问题：

- 发生了什么？
- 为什么现在告诉我？
- 我可以做哪一个最小动作？

例如：

```text
Claude 在 api-server 等待你的权限，已经 3 分钟。
[查看请求] [稍后 10 分钟]
```

而不是：

```text
Claude 状态：attention
```

### 以用户意图为中心，而不是以 agent 事件为中心

hook 事件是事实来源，不是用户界面。`tool.start`、`turn.done` 等事件应先转换成用户能理解的意图：需要批准、仍在工作、已完成、发生错误、可以恢复。

### 主动但不自作主张

宠物可以主动发现问题，但未经用户确认不应执行有风险或不可逆动作。尤其是：删除、移动文件、提交代码、发送消息、修改 agent 配置，都必须先展示目标和影响。

## 核心服务闭环

### 开始工作：恢复上下文

触发：用户回到电脑、解锁、打开工作区或主动点击宠物。

宠物给出一张“回来了吗”卡：上次停留的项目、当前未完成事项、离开期间变化。主按钮是「继续」，次按钮是「查看全部」。

### 工作中：只在有行动价值时打扰

触发：某个 agent 等待输入、权限、错误处理或外部资源。

宠物表情变化，气泡显示来源和最小动作；普通工作事件只更新工作台，不改变桌面表情。

### 离开后：生成交接

触发：用户离开一段时间后回来。

宠物不复述日志，只给“完成 / 等你 / 仍在运行 / 出错”的变化摘要。每一项都能打开对应任务。

### 卡住时：降低下一步成本

触发：错误重复出现、任务长时间无进展或用户手动说“卡住了”。

宠物可建议查看最近错误、拆出下一步、向 agent 追问或先记录问题。建议必须可关闭，不能把“卡住”变成高频骚扰。

### 收工时：留下明天能继续的线索

触发：用户结束工作、关闭工作区或进入安静时段。

宠物生成一份简短交接：每个未完成任务停在哪里、下一步是什么、哪些 agent 仍在运行。用户可以编辑后保存，第二天从一条入口恢复。

### 平时：成为低成本的记忆入口

触发：用户想到一件事、看到一段文字或听到一句话。

快捷键/语音/拖拽到宠物都可以捕获；宠物只确认“记下了”，具体整理在工作台中完成。

## 服务优先级

### 第一阶段必须做

1. 单宠物桌面和全局状态聚合；
2. 工作台：source → task/session → 详情，第一阶段先接 agent；
3. 需要用户处理的事项队列；
4. 上次停留位置、下一步和一键恢复；
5. 快速捕获和跨天交接；
6. 统一的隐私、安静模式和通知强度控制。

这些能力直接回答“我该做什么、从哪里继续、离开时发生了什么”。

### 第二阶段增强

- 从 agent 最后一条回复中提取可编辑的下一步；
- 本地模型辅助总结离开期间变化；
- 自定义规则：特定项目、agent 或时段的提醒策略；
- 一键打开项目、最近文件、错误位置和会话窗口；
- 用语音完成捕获、查询和“带我继续上次任务”。

### 第三阶段探索

- 跨 session 的 Task 聚合和用户手动合并；
- 后台任务、CI、日历和 issue 的统一状态；
- 更丰富的陪伴记忆和个性化仪式；
- 多设备之间共享工作交接，但仍由用户明确选择同步内容。

## 不应该做什么

- 不把“连续在线时间、打卡天数、被提醒次数”作为核心成功指标；
- 不用宠物的悲伤、惩罚、掉血或失望逼用户工作；
- 不每隔固定时间打断用户证明自己有用；
- 不让宠物替用户自动执行不可逆动作；
- 不把所有 agent 日志搬到桌面上；
- 不把任务管理、健康提醒、情绪陪伴混成一个没有优先级的面板；
- 不让用户为了维护宠物的状态而产生第二份待办工作。

## 成功标准

产品成功不应是用户盯着宠物更久，而应是：

- 用户离开后能更快恢复到正确任务；
- 需要用户处理的事项更少被漏掉；
- 用户能用一句话把想法放下来，并在合适时找回；
- 每天结束时，未完成任务都有清楚的停点和下一步；
- 用户主动降低提醒或完全关闭桌宠时，核心工作服务仍然可用；
- 用户能清楚知道数据从哪里来、为什么提醒、如何删除。

建议观测的指标是恢复任务所需时间、提醒后的有效动作率、过期/误报率、捕获内容的完成率和用户主动使用工作台的频率，而不是桌宠驻留时间。

## 最终方向

桌宠应该从“一个会动的注意力计时器”变成“一个有温度的工作记忆入口”：

- 它陪着你，但不监视你；
- 它提醒你，但不催促你；
- 它知道发生过什么，但把决定权留给你；
- 它不替每个 agent 造一个角色，而是替你把多个 agent 的工作整理成下一步。

这也是单宠物方案成立的前提：桌面角色保持稳定，复杂度进入可展开的服务层，陪伴和实用性才不会互相争夺同一块屏幕。
